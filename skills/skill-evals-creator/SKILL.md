# Skill Evals Creator

把技能作者脑中的“应该能用”变成可以交给评测执行者的具体任务。交付的是用例及其输入和成功标准；用例写好了不等于技能已通过测试。

方法依据：[Agent Skills — Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)。本技能把其中的用例设计方法整理成中文共创流程；离线使用不需要重新访问网页。字段约定见 [用例格式](references/eval-format.md)，不会要求用户先学 JSON。

## 1. 识别当前起点

优先使用已提供的信息，不重复询问：

| 用户已有的材料 | 行动 |
|---|---|
| 技能目录或 SKILL.md | 读取用途、输入输出、分支、失败处理；只按需读取关联脚本和资料，再写首批用例 |
| 只有用途描述 | 提炼“谁会怎么问、提供什么、得到什么”；区分用户规则与临时假设 |
| 不知道怎么写测试 | 读取 [新手引导与示例](references/guided-design.md)，先展示草案，再问影响预期结果的缺口 |
| 已有 evals | 保留 ID、用户字段和已有有效场景，补缺口，避免全量重写 |
| 有失败输出、评分或反馈 | 读取实际材料，把问题转成回归场景；按第 4 节补断言 |

若连待测技能的用途都未知，先问一个能推进的问题：“这个技能平时帮你做什么？贴技能内容，或者给一句你会对它说的话就行。”此时可解释一种用例的样子，但不要把猜出的业务写成正式用例。若用途已知、只是没有技能文件，可以依据用途产出草案并注明依据有限。

## 2. 从具体草案开始引导

用用户熟悉的话说明：“一个用例就是一句真实请求，加上你希望看到的结果；需要材料的话再带一份样本。”

每轮通常只问一个影响结果的问题，相关问题最多合并三个。不要同时要求用户交齐技能路径、测试维度、覆盖率、断言和运行环境。用户不知道如何回答时，给一个明确建议及可修改的示例；不要重复原问题。

能依据现有规则决定的格式、样本规模等小事直接采用默认值。涉及业务取舍（例如空值是删除还是保留）时，优先读技能规则；仍未知则提一个具体问题。等待答案期间可完成其他独立用例。未确定的取舍写入草案说明，不把它写成唯一正确的断言。

## 3. 构造首批用例

默认先写 2–3 个，用户指定数量时遵从用户；可合并维度，不为凑数量堆重复请求：

- 一个代表性任务，验证技能主要价值。
- 一种真实表达或上下文变化，观察技能能否在省略、口语或不同材料下完成任务。
- 至少一个相关边界，例如输入缺字段、存在冲突、材料为空或任务超出已声明能力。

每个用例包含真实请求、可观察的成功描述和可选输入文件。请求用最终用户的口吻，不在请求里塞入全部实现步骤或评分答案，除非真实用户确实会提供这些步骤。变化应影响任务判断，不能仅替换几个同义词。

预期结果既要说明交付物，也要说明关键事实和边界行为。缺输入用例可能以“指出缺少哪份材料并请求补充”为成功，不必强求生成最终文件。输出质量评测默认在技能已加载的条件下进行；不要用它声称测出了自动触发率。只有明确评估路由时，才单独设计应触发与不应触发的数据集，并说明另需触发评测环境。

样本应小而足以暴露问题。可自行创建合成材料，标明“合成”，不要捏造用户的真实数据。必须依赖未提供材料的用例保持草案状态；若故意测试缺文件，在说明中记录这个设计，不伪装成正常输入已准备好。

## 4. 根据结果细化断言

没有运行结果时，先交付 prompt、expected_output 和 files。已明确的成功标准要现在写清；不必强行拆成大量 assertions。用户明确要求预写断言时可以提供，但标注为“尚未经过运行校准”，不能为写断言而替用户运行任务。

拿到首轮输出后，逐例检查预期与实际差距，写出单项、可验证的 assertions。格式解析、计数和计算优先建议程序检查；事实覆盖可通过输出内容核对；美感、语气和实用性留给人工反馈，必要时给观察维度，不伪装成精确布尔判断。

不要把“专业”“质量好”当断言，也不要因实际输出不同就放宽原有正确标准。若预期本身错了，解释依据、保留变更记录，再修正。评分应引用实际产物中的证据；没有输出就不能填写通过率。

若用户要求进一步安排对照运行，读取 [运行交接](references/run-handoff.md)。当前请求仅要求创建用例时，到可运行的交接材料为止。

## 5. 落盘、检查、交付

有目标技能目录时，默认写到该技能的 `evals/evals.json`，不要误写进本技能包。没有目标目录但用途和名称已知时，在当前工作区 `skill-evals-drafts/<skill-name>/evals/` 保存草案；用户只要对话中的建议时不强制创建文件。目录名未定可采用描述用途的临时英文名，并说明映射。

需要说明时同时写 `evals/notes.md`，记录每个 ID 的覆盖意图、材料来源（用户提供／合成／待提供）、临时假设、就绪状态，以及需要人工观察的点。未解决的业务取舍与缺失材料用例放在 `evals/pending-cases.md`，不混入就绪用例；若全都待定，仅交付待定草案，不创建一个看似可运行的空集。纯粹测试缺输入的完整场景仍可以就绪。

按 [用例格式](references/eval-format.md) 保存并检查 JSON。可运行随本技能提供的只读检查器：

```bash
python3 <本技能目录>/scripts/validate_evals.py <目标技能目录>/evals/evals.json
```

检查器只验证结构、ID 和所列输入文件，不能证明业务预期正确。另行阅读用例，核对覆盖是否有意义、事实是否来自输入、是否含未声明假设。现有文件中有自定义字段时保留并确认执行器契约；不宣称所有评测工具都兼容。

交付时简短说明保存位置、覆盖的场景、待定项和验证范围。给用户一句接得上的下一步，例如“拿这三例各跑一次，把输出发来，我再帮你补可判定的断言”。只报告实际做过的验证，不生成虚构的 grading、timing 或 benchmark 文件。

维护本技能时可使用 [自身评测用例](evals/evals.json)。这些是待执行的行为用例，不代表已经通过模型评测。
