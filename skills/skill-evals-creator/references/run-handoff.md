# 将用例交给评测执行者

创建或补充用例后，先按主文档第 6 节审查覆盖情况，结论为“设计基本充分”才读取本文并衔接实际执行；需要补改时先反馈方案，用户确认后补充并复审，证据不足时先补齐信息，均不直接运行。用户明确只要设计或不要运行时跳过执行。默认执行本轮审查范围内全部就绪用例，每例一次、只跑候选技能；向 `skill-evals-executor` 传递对应 ID 和 `candidate-only` 范围。创建流程包含这一轮测试，无需重复请求运行授权，但不扩大为额外付费调用或外部系统变更。

每次运行交接覆盖审查报告及通过结论（仅供调度方核对，不传入被测模型）、技能版本、用例 ID、prompt、实际输入文件和输出目录。expected_output 与 assertions 留给评分方；不注入被测模型上下文，以免泄露答案。

建议在技能目录旁保存独立工作目录：

```text
<skill-name>-workspace/iteration-1/eval-1/
  with_skill/outputs/
  without_skill/outputs/  # 仅在用户要求无技能对照时创建
```

默认候选单组运行不计算对照差值。用户要求对照时，两组使用同一请求、等价输入和相同模型配置，并分别使用干净上下文及隔离文件副本。基线环境不能通过自动发现、父级指令或历史消息加载待测技能；做不到时注明对照受到污染，不能据此判断技能贡献。比较修订版本时，在修改前保存旧版快照，使用 `old_skill` 作为基线；拿不到旧版就报告限制。

实际运行后才记录产物、逐条断言证据与结果，以及可获取的时间和 token 数据。缺失的测量值标为不可用，不能用估算冒充实测。没有输出的阻断运行单独记录原因，不当作有证据的 PASS。小样本先看逐例结果；单次运行不能证明稳定性。

每轮完成或受阻都要保存测试报告并交付路径，列出逐例状态、实际证据、失败或阻断原因；准备材料和结构校验不能替代真实运行。执行器不可用时按主文档保存未执行报告，不伪造产物。

反馈回流时，同时看失败条件、人工对产物的意见和执行过程。重点检查：断言是否真的区分质量；两组都失败是否来自错误标准或环境问题；同一例忽好忽坏是否来自输入或规则歧义。机械格式检查即使两组都通过，也可作为回归保护保留，不能把它当作技能新增价值的证据。

改进时修一般规则，不围绕某一条测试答案特判。新增未见过的相关输入，保留原失败场景作为回归用例，并在新的 iteration 目录记录后续结果。
