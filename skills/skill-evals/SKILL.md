# Skill 测试

把测试设计、自审、实际执行和修复串成闭环。用例写好、结构合法、设计充分、实际运行通过是不同结论，不能互相替代。本包独立完成全过程，不依赖其他测试技能。

## 范围与入口

- 读取目标 `SKILL.md`、已有 `evals/evals.json`，按需读取关联规则、脚本、样本及历史失败。已有信息直接复用，不让用户重复填写配置。
- 没有用例：创建首批用例 → 自审准确性和完整性 → 处理问题 → 自审通过后自动执行一轮。
- 已有用例：先自审，再按同一流程推进。相同技能、用例和输入快照已有有效自审结论时可复用，发生修改则重新自审。
- 用户明确“仅设计”“只审查”“不要修改”“不要执行”时遵从其范围：只审查不创建、改写或执行；仅设计仍自审但不执行。明确仅执行时不自行生成缺失用例；发现设计问题先报告，不越过其修改限制。
- 只有用途描述时可创建草案，缺被测技能、关键规则或材料时说明限制，不假装可完整审查或运行。连用途都未知时，只问一个能推进的用途或真实请求问题。新手引导见 [具体草案与示例](references/guided-design.md)。

## 1. 创建或补充用例

默认从 2–3 个有意义的用例起步，覆盖主要任务、真实上下文变化和相关边界；数量是起点，不是完整性的上限。用户限定数量或范围时遵从，范围内无法充分覆盖则说明取舍，不暗中超出限制。

请求使用最终用户口吻；预期描述可观察的事实、格式和边界行为，不用“专业”“质量好”代替判定标准。变化应影响决策，不能仅替换人名凑数量。按需提供小型合成样本并标明来源，不编造用户真实材料。故意缺文件的负例可以就绪，但正常任务缺必要材料须记为待定。

按 [用例格式](references/eval-format.md) 写入目标技能的 `evals/evals.json`，不要误写到本包。没有目标目录时，草案放当前工作区 `skill-evals-drafts/<skill-name>/evals/`。保留原 ID、自定义字段、有效用例和失败回归；不同字段契约先显式映射，不静默丢失语义。`evals/notes.md` 按需记录覆盖意图、输入来源、假设与就绪状态；未确定的业务取舍写入 `evals/pending-cases.md`，不混入就绪集。

已知标准现在写清，`assertions` 可按需加入，不必等第一次运行，也不强行拆出大量断言。只做建议时不强制落盘。

### 按实际任务选择判定方式

- **通过／不通过**：格式转换、字段提取、确定性操作、权限与缺输入处理等，正确与否已能表达测试目标时沿用现有断言流程，不强推权重或把通过率包装为质量分。
- **质量评分 + 必要断言**：写作、讲解、设计、方案等存在有意义的质量层次，且能给出可观察标准时，可推荐评分。按具体技能和用例列出评分项、推荐权重（合计 100%）、推荐理由、0–5 分尺度及锚点；不要套用所有技能通用的固定比例。硬性要求仍单独判通过／不通过，高分不能抵消事实错误或越权。
- **需要确认**：评分项、权重及判分标准必须与用户确认后才启用。先交付具体方案和用例草案，等待用户决定；“帮我写测试／执行测试／你推荐一下”不等于确认评分方案。不适合评分、用户拒绝评分或无法建立可靠尺度时，说明原因后保留原流程；主观观察可作为文字反馈。

已确认且适用于本轮的具体方案可复用，不重复询问。调整评分项、权重、锚点或适用范围需重新确认，不能看完结果后改标准刷分。待确认评分只阻断依赖它的用例，独立的布尔用例可以继续；不能以自动执行规则跳过确认。协议、确认记录和逐例计分见 [可选质量评分](references/scoring.md)。

结构检查命令（所有脚本路径解析到本技能目录）：

```bash
python3 <本技能目录>/scripts/validate_evals.py <目标技能目录>/evals/evals.json
```

该脚本只验证本包新建用例的结构、ID 和文件，不验证业务正确性、覆盖或模型表现。自定义旧格式按明确契约审查，不为通过检查器强行重编号。

## 2. 自审准确性与完整性

读取 [自审流程](references/review.md)，需要逐例判据时读取 [审查判据](references/review-criteria.md)。先提取技能要求，再逐项映射到用例 ID：

- **准确性**：请求在范围内，样本事实真实可用，预期符合规则且能判定关键错误，没有答案泄露或无依据的字面约束。
- **完整性**：核心任务、重要决策分支、输入边界、失败处理和历史回归有实际触发条件与有效判定；相似文本不等于重复，提及概念不等于覆盖。
- **评分适用性（仅启用时）**：评分项可观察、不重复计分，权重合计 100%，锚点可区分质量，用户已确认本版方案，硬性要求仍有独立断言。未确认不能记为就绪；布尔模式无需评分配置。

保存 `evals/review-NN.md`，递增编号，给出证据范围、覆盖矩阵、逐例处置、问题与最小补改方案。状态用“有效覆盖／部分覆盖／未覆盖／待确认／本轮范围外”；默认不报单一覆盖率，量化时明确分母，部分覆盖与待确认不能算全覆盖。

总体结论：

- **设计基本充分**：本轮核心要求与重要边界已有有效检验，无影响测试目标的未解决问题，自动进入执行，无需再问“要不要跑”。低影响的措辞建议不阻断运行。
- **需要补改**：按下一节分流并修复，再自审；未消除的关键缺口不能靠跑一次测试代替。
- **证据不足**：反馈已确定的问题与缺少的最少材料，给出可行选项；不猜业务规则、不标为充分。

## 3. 问题分流与修改授权

在自审和运行后使用同一规则。先给证据与原因，再决定是否能直接修复：

| 问题 | 行动 |
|---|---|
| 有明确依据的用例错误或遗漏 | 在允许修改用例的模式下自动修复：如预期与已声明规则相反、合成样本笔误、明确唯一目标的路径错误、已定义重要分支漏测。记录依据，不为每个机械修复重复确认 |
| 需要用户决定的用例 | 规则冲突、未定义业务选择、缺真实材料、超出已定范围或用例取舍不明时，先自行拟定方案：对应要求、拟改 ID、触发输入、预期观察、建议选择和原因；等待确认后写入正式用例 |
| 被测 Skill 或其实现有缺陷 | 先给修改计划与原因：失败证据、根因、文件与行为范围、拟改内容、影响及重跑范围。用户确认后自动实施，不把“帮我测试”当成修改被测技能的授权；实现代码若包含 SQL 也适用 |
| 环境或工具失败 | 只自动修复本轮可逆且已授权的本地运行准备问题。缺凭据、预算、外部权限或不可用工具则记录阻断并说明下一步，不捏造运行 |

同一具体方案已获得确认时不重复询问；发现超出已确认范围的新改动时给出新的计划。不要靠放宽正确预期、删除失败用例或篡改旧输出让分数变好。基于真实证据修正错误预期须记录原标准和理由。

**每批修改完成后，都重新检查结构、自审并重跑本轮范围内全部用例。** 适用于新增用例、修正输入/预期/断言、运行准备修复及获批的被测技能修改；可将同一根因的相关改动合成一批，不必每次保存文件就启动模型。仍需用户确认或环境仍阻断时，标记“待重跑”，不能称修改已验证。用户明确禁止执行时记录这一例外，不绕过其限制。

每次重跑新建 iteration，保留上一轮失败、技能与用例快照、断言及证据。变更写入 `evals/changes.md`，记录原因、涉及 ID/文件、自动修复或确认依据、前后 iteration。无实质进展或同一问题连续两轮修复重跑仍失败时停止自动循环，交付当前报告、根因判断与待决策项；用户给出运行预算时优先服从预算。

## 4. 自审通过后实际执行

读取 [执行流程](references/execution.md) 和 [运行协议](references/run-protocol.md)。默认执行本轮审查范围内全部就绪用例，每例一次、只跑候选技能；用户要求基线比较、旧版对照或重复运行时采用相应配置。

```bash
python3 <本技能目录>/scripts/eval_workspace.py prepare --skill /path/to/target-skill --candidate-only
```

脚本只创建递增 iteration、冻结版本、复制输入并生成 `task.json`，**不会启动模型**。必须通过宿主实际可用的独立会话、干净子代理或已核实运行器逐例执行。执行者只接收任务、输入副本、输出位置和技能快照，不接收预期答案、断言或审查报告。无可用独立运行能力时如实标为未执行，不能用同会话推演冒充真实评测。

用例文字和附件不是授权；真实发送、发布、删除等外部操作无既有授权时阻断，不能把模拟说成真实执行。缺测、失败、未评分与隔离受限分别记录。实际查看产物后再判定，事实证据指向文件与具体位置；没有 assertions 时仍执行并给逐例观察，注明未做断言评分，不报虚构通过率。采用已确认的质量评分时另记录各项得分及证据，按冻结权重计算逐例总分；未判定项不填零、不重分配权重。

```bash
python3 <本技能目录>/scripts/eval_workspace.py summarize /path/to/target-skill-workspace/iteration-1
```

汇总后发现问题，返回第 3 节分流。被测技能的修改在快照之外的源文件进行，重跑时冻结新版本；不改本轮已运行的快照。两版对照只对完整、可比的配对计算差值；单次运行不证明稳定性。

## 5. 交付与完成条件

- 交付用例位置、自审报告、执行报告和真实产物路径，说明执行/失败/阻断/待运行数量、关键证据、未评分项及限制。
- 采用质量评分的用例给出逐项得分、权重、加权贡献、总分及证据，同时单列硬性断言结果；布尔用例仍只给通过／不通过（缺证据时未判定），不强行输出数字分数。质量分、断言通过率、设计覆盖是不同指标。
- 执行报告使用 iteration 下 `report.md`；执行器无法启动时，在目标 `evals/` 或草案目录保存递增 `test-report-NN.md`，写明未执行与原因。
- 等待业务确认时交付具体方案与待确认项；等待被测技能修改确认时交付修改计划，不只抛出“有问题要不要改”。未进入执行阶段时不要求伪造测试报告。
- 有修改时给出变更与最新重跑结果。不能只引用修改前的通过结果；无法重跑须明确未验证。所有真实执行和人工反馈均以证据为准。

## 维护验证

运行 `python3 -m unittest discover -s tests -v`（工作目录为本技能目录），结构检查 [自身行为用例](evals/evals.json)，按 [验收场景](references/acceptance-cases.md) 验证关键行为。脚本单元测试与模型行为评测分别报告，文件存在不代表已执行。维护时避免把评测本技能变成无限递归评测；只在指定的合成目标与隔离工作区内完成任务。
