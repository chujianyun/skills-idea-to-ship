# 用例审查判据

逐例审查时按实际问题查阅。判断依据始终来自目标技能与输入材料，不把下面的例子变成所有技能的必测清单。

| 问题 | 判断信号 | 应给出的证据或建议 |
|---|---|---|
| 任务错配 | 技能只提取行动项，用例却要求情绪分析且期待正常交付 | 指出技能用途、Case 请求与错误预期；若是负例，应期待正确的越界处理 |
| 预期错误 | 技能要求未知负责人待定，用例要求猜测负责人 | 引用规则与该例预期，修正标准；不能因模型也这么做就接受 |
| 虚假覆盖 | 要测冲突处理，样本却只有单一版本；或只检查生成了表格 | 展示缺少触发条件或判定标准，标部分/未覆盖 |
| 标准过弱 | “结果合理”“输出文件存在”能让核心内容错误也通过 | 给出一个会漏过的具体错误，建议补可观察的事实或行为 |
| 标准过严 | 未规定顺序却要求逐字一致；正确同义表达会失败 | 保留事实要求，放宽无依据的呈现约束 |
| 不可执行 | 正常场景所需附件不存在，路径契约不明，依赖无法满足 | 区分故意缺输入与材料遗漏；只阻断依赖该材料的判断 |
| 答案泄露 | prompt 或执行者收到的材料包含隐藏评分答案或全套技能步骤 | 区分真实用户必要约束与人为泄题，说明它如何绕过待测能力 |
| 重复冗余 | 同一分支、等价输入和判定，只替换无关人名 | 列明等价关系、保留 ID，以及删除不损失哪条覆盖 |
| 有价值的相似 | 相似请求分别验证明确字段与缺失字段、不同文件格式或历史回归 | 保留；说明独立失败模式，不按文本相似度去重 |
| 测试层混淆 | 手工加载技能的输出用例被算作自动选择技能的证据 | 单列路由数据和所需执行环境；输出测试仍可保留 |

## 重复用例的取舍

先比较 `(前置条件与输入特征，决策分支，预期行为，能捕捉的失败)`，再讨论成本。同一分支不必只有一个用例；不同语言、格式、历史失败或高风险回归可以提供独立信号。重复运行同一任务以观察波动是执行配置，也不等于设计冗余。

缺少采样意图时将相似用例标为“合并候选，需确认独立目的”，不要断言一定无用。若 notes 已清楚说明只改姓名且无独立目的，可直接建议合并。高通过率或候选/基线都通过，不是删除基础正确性测试的理由。

把多条简单用例合成复杂大例，可能让早期失败遮住后续分支；评估是否仍可独立判定。建议删除时写清保留用例及覆盖承接，不能只说“太重复”。

## 充分性与遗漏

以最少但有效的用例覆盖重要义务。对于条件规则，检查条件成立和真正相关的不成立情形；对于有状态流程，检查关键状态转换。仅在这些行为确实存在于目标技能时应用，避免笛卡尔积式穷举。

规范没有定义某情况的正确行为时，先列“规范缺口”，例如两条不同截止日期应该保留哪条。可以给选择建议，不能把偏好写成唯一正确断言。用户本轮仅检查某些 ID 或某种输入时，结论明确限定范围，不能把其他范围省略后宣称整个技能测全。

## 证据与建议的写法

有效示例：

> P1，Case 4 预期“将最近出现的人名填作负责人”，与 SKILL.md 的“未明确负责人则待定”冲突。该例会把编造归属判为正确。将预期改为待定，并检查其他行动项的负责人仍来自原文。关联 R2；当前唯一用例无效，因此 R2 未覆盖。

无效示例：

> 覆盖不全面，建议增加异常测试、边界测试、安全测试。

补测建议至少给出触发条件和观察点，例如“空白会议记录 → 明确无可提取内容，不生成虚构行动项”，并说明它来自哪条规则。未执行时不要给通过率、实际失败次数或声称已经证明某个错误实现会通过。
